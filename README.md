# Hello Tennis Video — MVP 0.1

> **v0.2.3 progress-watchdog**: FFmpeg 진행률 파이프 교착 방지, GPU 초기화 watchdog/fallback, 실제 out_time/frame/speed/ETA 진행률을 포함합니다. 이전 버전 서버가 실행 중이면 완전히 종료한 뒤 이 폴더의 `run_windows.bat`를 다시 실행하세요.


실제 경기 영상을 빠르게 라벨링하고, 포인트 승자를 입력하면 테니스 점수를 자동 계산하며,
경기 구간만 이어 붙인 영상 또는 스코어보드가 포함된 방송형 영상을 렌더하는 첫 번째 구현입니다.

## 현재 구현된 기능

- 여러 영상 파일 불러오기
- `ffprobe`를 통한 원본 메타데이터 읽기
- 4K HEVC용 브라우저 프록시 생성
  - 가능한 환경에서는 `hevc_cuvid` + `h264_nvenc` 우선 시도
  - 실패 시 NVENC 또는 CPU x264 fallback
- 파일별 4점 코트 Calibration 저장
- 원본 시간 기준 Point START / END 라벨링
- Timeline에서 Point 선택/수정/삭제
- Team A / Team B Winner 입력
- Winner sequence에서 스코어 전체 자동 재생성
- Standard / No-Ad 기본 지원
- 서버 순서 관리
- 코트 위치 기준 스코어보드 행 swap 데이터
- 프로젝트 JSON 자동 저장/불러오기
- 여러 원본 파일의 Point를 하나의 경기 영상으로 FFmpeg export
- ASS 기반 방송형 스코어보드 burn-in export
- `source time`을 그대로 유지하는 데이터 구조

## 실행 조건

1. Windows 10/11 또는 macOS/Linux
2. Python 3.10 이상 권장
3. FFmpeg / FFprobe가 PATH에 있어야 함

Windows에서는 `run_windows.bat`을 더블클릭합니다.

실행 후 브라우저에서 자동으로 다음 주소가 열립니다.

`http://127.0.0.1:8765`

## 화면 구성과 사용 순서 (v0.6.0)

화면은 **왼쪽 영상 · 오른쪽 탭 4개**다. 진행 상황과 메시지는 위쪽 막대 한 곳에만 나온다.

- **왼쪽**: 영상, 재생 속도(0.25×·0.5×·1×), 포인트 시작/끝 버튼, 그 아래 **타임라인 막대**
  (회색 칸 = 기록한 포인트, 연두 선 = 서브, 회색 선 = 랠리 타구, 클릭하면 그 장면으로 이동)
- **준비** 탭: 할 일 체크리스트. 끝난 단계는 초록 점, 남은 단계는 주황 점으로 표시되고 탭 이름 옆에 `3/4`처럼 남은 수가 보인다.
  1. 영상 — 재생용 사본(프록시) 만들기
  2. 코트 위치 — 모서리 4곳 찍기(가까운 왼쪽 → 가까운 오른쪽 → 먼 오른쪽 → 먼 왼쪽), 필요하면 "라인에 맞춰 보정"
  3. 선수와 규칙 — 팀별 애드/듀스 선수 이름, 처음 위치. 서브 순서·왼손잡이·노애드 등은 "규칙 더 보기"
  4. AI 준비 — 공 추적·자세 인식 패키지 설치, Gemini 키
- **포인트** 탭: 스코어, 선택한 포인트의 승자(A/B)·시작/끝 수정·삭제, 포인트 목록(클릭 = 그 위치로, 더블클릭 = 재생)
- **분석** 탭: **분석하기** 한 번이면 공 추적(서브 속도·구질, 랠리 타구 찾기) → 타구 종류 판정이 차례로 돈다.
  판정 방식·범위·화질과 단계별 재실행은 "고급 설정". 아래에 요약 숫자, 서브 구질·1st/2nd, 선수별, 타구 목록, 서브 실측 표,
  그리고 **영상 만들기**(분석 대시보드 영상 · 포인트만 이어 붙이기 · 방송형)
- **채점** 탭: 정답 키(X/F/D/V/M/L, Shift = 먼 쪽 선수)로 기록한 정답과 분석 결과를 비교한 정확도
- **프로젝트** 메뉴(오른쪽 위): 다른 프로젝트 열기 / 다른 이름으로 저장 (평소엔 자동 저장)

디자인 원칙: 작업 도구라서 익숙함과 훑어보기 쉬움이 우선. 강조색은 테니스공 연두 하나(실행 버튼·현재 위치·서브),
팀 색은 A 하늘색 / B 살구색. 서체 Pretendard(인터넷이 없으면 맑은 고딕), 숫자는 고정폭 숫자.

**내보낸 영상도 같은 디자인** (`analysis/render_style.py`가 색·글꼴을 한곳에서 정함):
- 분석 대시보드 영상: 어두운 패널에 한글 라벨 — 타구 수 · 포핸드/백핸드(비율 막대) · 타구 속도(실측이면 연두) /
  타구별 속도 막대(서브 연두, 스트로크 회색, 최근 것만 진하게) · 서브 위치(최근 = 연두 원, 폴트 = 빈 원).
  타구마다 왼쪽 위에 이름·구질·속도·선수가 담긴 카드가 1.6초 뜬다. 예전 오른쪽 아래 프레임 번호는 뺐다.
- 방송형 영상 스코어보드(`analysis/scoreboard.py`): 팀 색 점 · 이름 · 서브하는 팀의 연두 공 · 게임 · 포인트(돋운 칸),
  세트는 한 세트가 끝난 뒤부터. 포인트마다 그림으로 그려 영상 위에 얹는다(FFmpeg 자막 기능 없어도 됨, Pillow가 없을 때만 예전 자막 방식).
- 공 궤적은 꼬리 끝으로 갈수록 가늘고 흐린 연두, 현재 공은 연두 링. 선수 뼈대는 흰 선에 어두운 테두리.
- 글꼴: 처음 내보낼 때 Pretendard 4종을 `models/fonts`에 내려받는다(인터넷이 없으면 맑은 고딕).

방송형 Export는 FFmpeg의 `subtitles`/libass 필터가 필요합니다.
Windows에서는 `Malgun Gothic`을 ASS 폰트명으로 사용합니다.
FFmpeg 빌드에 libass가 없으면 일반 `Match_GameplayOnly.mp4` Export는 정상 동작하지만 방송형 burn-in은 실패할 수 있습니다.

## 왜 이 순서인가

첫 프로그램에서 가장 중요한 산출물은 완전 자동 AI가 아니라 실제 촬영 조건의 정답 데이터입니다.
이 MVP로 `POINT_START / POINT_END / WINNER`를 빠르게 누적하면 다음 버전부터 Formation/Temporal 모델의 Recall, Precision, MAE를 실제 수치로 비교할 수 있습니다.

## Formation 분석 (옵션 버튼)

UI의 `Formation 분석 (옵션)`은 다음 단계용 실험 기능입니다.

먼저:

```bash
pip install -r requirements-ai.txt
```

그 뒤 프록시와 4점 Calibration이 저장된 파일에서 실행하면:

- YOLO 사람 검출
- 코트 좌표 내부 사람만 유지
- near/far 사람 수와 팀 spread 등 Formation feature 생성

결과는 `cache/<file_id>_formation.json`에 저장됩니다.

이 Change Point는 **포인트 정답 판정이 아니라 라벨링을 빠르게 하기 위한 경계 후보**입니다.

## 실제 FFmpeg 프록시 진행률

프록시 생성은 백그라운드 FFmpeg 작업으로 실행되며 `-progress pipe:1`의 실제 값을 읽습니다.
상태 영역에는 생성 중 다음 정보가 표시됩니다.

- 실제 완료율 (%) — FFmpeg `out_time / 원본 duration`
- 실제 처리된 영상 시간 / 전체 영상 길이
- 현재까지 처리한 frame 수
- FFmpeg 처리 속도 (`speed`, 예: `7.35x`)
- 현재 처리 속도 기준 남은 예상 시간(ETA)
- 사용 중인 처리 방식 (`NVIDIA decode + NVENC`, `NVENC`, `CPU x264`)

NVIDIA 경로가 실행 환경에서 실패하면 다음 방식으로 자동 재시도하며, 게이지도 실제 새 시도 진행률로 갱신됩니다.


## 프록시 실제 진행률

프록시 생성은 FFmpeg의 `-progress pipe:1` 값을 읽어 실제 진행률을 표시한다.

표시 항목:

- 실제 처리 퍼센트
- 처리된 영상 시간 / 전체 영상 시간
- 처리 프레임 수
- FFmpeg 처리 속도 (`x`)
- 남은 예상 시간(ETA)

### 업데이트 후 이상한 오류가 보일 때

기존 `run_windows.bat` 서버가 켜진 상태에서 파일만 덮어쓰면 웹 화면과 Python 백엔드 버전이 달라질 수 있다.
반드시 기존 검은색 서버 창을 완전히 닫고 새 폴더의 `run_windows.bat`를 다시 실행한다.

이번 버전은 프록시 실행 전에 서버 API 버전을 검사하고, 이전 서버가 실행 중이면 재시작 안내를 표시한다.
또한 ffprobe/프로젝트 JSON이 비어 있거나 손상된 경우 Python의 원시 `json.loads(None)` 오류 대신 원인을 설명하는 오류를 표시한다.

## AI 기능 설치 (v0.2.4+)

Formation 분석용 패키지는 기본 MVP와 분리되어 있습니다. 이제 명령 프롬프트에서 직접 설치할 필요가 없습니다.

1. 프로그램 상단의 `AI 기능 설치` 버튼을 누릅니다.
2. 프로그램이 현재 실행 중인 Python 인터프리터로 `requirements-ai.txt`를 설치합니다.
3. 설치 상태는 `AI 미설치 → AI 설치 중 → AI 준비됨`으로 표시됩니다.
4. 설치가 끝나면 `Formation 분석 (옵션)` 버튼이 자동으로 활성화됩니다.

처음 설치할 때 `ultralytics`와 PyTorch 관련 패키지가 함께 설치될 수 있어 인터넷 속도와 PC 환경에 따라 시간이 오래 걸릴 수 있습니다.
Formation 분석을 처음 실행할 때는 `yolo11n.pt` 모델 파일도 최초 1회 다운로드될 수 있습니다.

AI 설치가 실패하면 상태창에 pip 오류가 표시됩니다. 이 경우 `run_windows.bat`를 실행한 Python과 pip가 같은 인터프리터인지 프로그램이 자동으로 맞추도록 `python -m pip` 방식으로 설치합니다.

## AI 샷 분석 (v0.3.0) — TennisApp 영상분석 이식

경기 영상을 넣으면 **포핸드/백핸드 횟수, 서브 구질(플랫·슬라이스·킥), 속도(km/h)** 를 분석한다.
TennisApp(`services/gemini/videoAnalysis.ts`)의 Gemini 분석 프롬프트·구조화 출력·검증 규칙(`videoSanityCheck.ts`)을 가져와 긴 경기 영상용으로 바꿨다.

### 사용법

1. Gemini API 키 준비 (https://aistudio.google.com/apikey)
2. 화면 아래 **AI 샷 분석** 패널 → `API 키 설정` → 키 입력 후 저장
   - 키는 `config/gemini.json`에만 저장된다. 환경변수 `GEMINI_API_KEY`가 있으면 그것을 우선 사용.
   - 모델 기본값은 `gemini-3.8-flash` (3.5 Flash 대비 입력·출력 단가 절반, 2026-10 기준 최신 Flash). TennisApp은 `gemini-3.5-flash`.
3. 범위 선택
   - **라벨된 포인트만 (권장)**: START/END로 찍은 포인트 구간만 분석. 빠르고 비용이 적으며,
     스코어 데이터(서버 순서·코트 위치)로 **서브를 실제 서버에게, 스트로크를 Team A/B에게** 귀속시킨다.
   - **영상 전체**: 라벨 없이 전체를 4분 단위로 분석. 선수 구분은 가까운 쪽/먼 쪽만 가능.
4. `샷 분석 시작` → 진행률은 상단 상태바에 표시. `분석 취소` 가능.

### 동작 방식

- 분석 구간을 최대 4분짜리 묶음으로 나눠 720p H.264 + 모노 오디오 클립으로 추출 (타구음도 판독 단서로 사용)
- 각 클립을 Gemini File API에 올려 **타구 1개 = event 1줄**(시간·샷 종류·구질·서브 번호/방향·결과·추정 속도)로 받음
- 횟수·구질별 평균/최고 속도·1st/2nd 성공률은 이 프로그램이 event를 직접 집계 (중복 제거, 포인트 내 1st/2nd 보정, 비현실 속도 제외)
- 결과: `cache/<file_id>_shots.json`, 구간별 응답 캐시 `cache/shots/` (같은 조건 재분석 시 API 재호출 안 함)
- 서브 목록/전체 타구 표의 행을 클릭하면 그 장면으로 이동

### 랠리·물리 규칙 보정 (v0.3.1)

Tennis-Vision의 `rally_decode` / `shot_physics` 개념을 옮겨, AI가 타구를 하나씩 따로 판정하면서 생기는
불가능한 순서를 집계 전에 자동 수정한다 (`analysis/rally_rules.py`). API를 다시 호출하지 않는다.

- **같은 쪽 연속 타구 금지**: 랠리는 near/far가 번갈아 친다. 비터비 디코딩으로 가장 그럴듯한 순서를 찾아
  신뢰도 낮은 '친 쪽' 판정을 수정한다. 사이에 놓친 타구가 들어갈 시간(1.2초 이상)이 있을 때만 같은 쪽 연속을 허용한다.
- **리턴은 리시버 쪽**: 서브 다음 첫 타구는 반드시 리시버 쪽이고 바운스 후 타구여야 한다 (리턴 발리/스매시 → 기타).
- **중복 타구 제거**: 같은 쪽이 0.5초 안에 두 번 → 한 번의 스윙.
- **랠리 중 서브 → 스매시**: 랠리 타구 직후 2.5초 안의 오버헤드 동작.
- **폴트 공 넘겨주기 / 서브 전 타구 제외**: 1st 폴트 뒤 리시버가 공을 쳐서 돌려주는 동작은 집계에서 뺀다.
- **결과 정합성**: 위너·에러는 랠리 마지막 타구만 가능하고, 리턴된 서브는 '인'이다.
  마지막 타구 결과가 **라벨된 포인트 승자**와 모순되면 결과를 '미확인'으로 돌린다.

보정 내역은 결과 화면 상단 `🔧 랠리·물리 규칙 보정`에 표시되고, 보정된 행에는 `보정` 표시가 붙는다.

- 공 궤적·스켈레톤·실제 바운스 위치 표시는 공 추적/자세 모델이 들어가는 2단계에서 추가 예정.

### 서브 속도 실측 — 공 추적 (v0.4.0)

`서브 속도 실측 (공 추적)` 버튼은 AI 추정이 아니라 **영상에서 공을 직접 추적해** 서브 속도를 잰다. Gemini 키 없이도 동작한다.

1. 라벨된 포인트마다 서브 구간의 원본 프레임(약 60fps, 실제 타임스탬프)을 읽는다.
2. **TrackNet**(yastrebksv/TrackNet, 최초 1회 `models/tracknet.pt` 43MB 자동 다운로드)으로 프레임별 공 위치를 찾는다.
   가로등 같은 정지 물체는 걸러내고, 끊긴 궤적은 운동 방향으로 이어 붙인다.
3. **바운스** = 공의 세로 속도가 위로 꺾이는 지점, **임팩트** = 토스 궤적이 끝나는 지점(또는 비행 시작점, 타점 높이 1.6~3.4m 확인).
4. 코트 4점 캘리브레이션으로 서버 위치·바운스 위치를 미터로 바꾸고, 비행시간과 거리로
   **공기저항을 보정한 초속**(레이더건이 재는 값)을 구한다: `d = ln(1 + k·v0·T) / k`.
5. 바운스 위치로 **인 / 아웃 / 네트 / 라인 근접(25cm 이내, 판정 보류)**, T·바디·와이드, 듀스·애드를 판정한다.
   폴트면 같은 포인트 안의 2nd 서브도 찾는다.

결과는 `cache/<file_id>_serves.json`. AI 샷 분석 결과가 있으면 서브 속도를 실측값으로 바꾸고(AI 추정치는 `speed_est`로 보존),
대시보드 영상의 `serve placement`에는 실제 바운스 위치가 찍힌다. 스코어 설정상 서버 코트와 실제 서브 위치가 다르면 경고한다
(경기 설정에 `Team A 시작 위치` 항목 추가).

샘플 경기(라벨 10포인트)에서 10개 중 8개 서브를 측정했다: 먼 쪽 서브 5개 모두, 가까운 쪽 서브 3/5.
가까운 쪽 서브는 임팩트 직후 공이 빠르고 흐려 놓치는 경우가 있다. 오차는 프레임 간격·캘리브레이션 기준 보통 ±3~7km/h로 표시된다.
필요 패키지: PyTorch, OpenCV, NumPy (`AI 기능 설치`로 설치). NVIDIA GPU가 있으면 자동으로 쓴다.

### 공 궤적 꼬리 · 선수 스켈레톤 (v0.4.2)

대시보드 영상 내보내기에서 `공 궤적`, `스켈레톤`을 켜면 영상 위에 그려 넣는다.

- **공 궤적**: 내보내는 30fps 영상에서 TrackNet으로 공을 찾고, 정지 물체를 걸러 궤적으로 이은 뒤
  최근 14프레임을 하늘색→노랑→빨강 꼬리와 파란 원으로 그린다 (6프레임 이상 이어진 궤적만).
- **스켈레톤**: YOLO pose(`models/yolo11m-pose.pt`, 최초 1회 자동 다운로드, Ultralytics/AGPL-3.0)를 4K 원본에 돌린다.
  먼 쪽 선수는 1080p에서 60px 정도로 작아서 먼 코트 영역을 원본 해상도로 잘라 한 번 더 돌린다.
  발 위치가 코트(±2.5m) 밖인 사람(옆 코트·벤치)은 제외한다.
- 1분 40초 영상 기준 약 8분 (자세 추정이 절반 이상). 끄면 기존처럼 빠르다.

### 3D 궤적 맞춤 (가까운 쪽 서브 보완)

코트 4점 캘리브레이션으로 카메라(초점거리·위치·방향)를 역산한다 (`analysis/flight3d.py`).
샘플 경기에서 카메라는 근거리 베이스라인 뒤 5.6m, 높이 3.6m로 계산됐고 네트 높이 재투영으로 검증했다.
가까운 쪽 서브에서 바운스 장면을 놓쳤을 때, 토스 지점(서버 베이스라인 면 위의 3D 점)에서 출발해
중력·공기저항을 받는 3D 궤적을 관측된 비행 점들에 맞춰 바운스 시각·위치와 초속을 구한다 (표에 `3D` 표시).
먼 쪽 서브는 공이 카메라 쪽으로 다가와 깊이와 높이가 구분되지 않으므로 이 방식을 쓰지 않는다.

### TrackNet 맞춤 학습 도구

```bash
python tools/ball_dataset.py cache/ball_dataset VIDEO1.mp4 VIDEO2.mp4 VIDEO3.mp4:215-406   # 자동 라벨 데이터셋
python tools/finetune_tracknet.py cache/ball_dataset --steps 6000                          # models/tracknet_ft.pt
python tools/eval_serves.py models/tracknet.pt models/tracknet_ft.pt                       # 라벨된 포인트로 비교
```

- 길게 이어진 궤적의 검출은 그대로, 몇 프레임 끊긴 구간은 앞뒤 운동으로 보간해 '놓친 프레임'의 정답으로 쓴다.
- 학습한 가중치는 `models/tracknet_ft.json`에 `{"use": true}`가 있을 때만 앱이 사용한다 (평가에서 나아졌을 때만 켠다).
- 첫 시도 결과(2026-10-09): 자동 라벨 기준으로는 놓친 프레임 재현율이 3% → 54%로 올랐지만,
  라벨된 10포인트 실전 평가에서는 궤적 커버리지가 0.869 → 0.822로 줄고 서브 속도가 교차검증된 값에서 벗어나
  **채택하지 않았다** (`models/tracknet_ft.json`의 `use: false`). 자동 라벨만으로는 한계가 있어,
  다음에는 사람이 확인한 정답 프레임을 일부 섞어야 한다.

### 정답(사람 확인) 기준 검증과 타구음 보정 (v0.5.0)

모델끼리 비교하면 어느 쪽이 맞는지 알 수 없어서, **어떤 검출 모델도 쓰지 않은 정답표**를 만들었다
(`cache/<file>_serves_gt.json`, 만드는 도구: `tools/gt_strips.py`, `tools/gt_view.py`, `tools/gt_serves.py`).
- 임팩트: 4K 원본을 프레임 단위로 보고 라켓-공 접촉 프레임을 직접 판정
- 바운스: 색상만으로 공을 추적(학습 모델 없음) + 확대 프레임으로 직접 확인
- 그 과정에서 3D 맞춤이 '인'으로 본 가까운 쪽 서브 3개가 실제로는 **네트 폴트**, 측정된 2개는 **서브가 아닌 샷**이었음을 확인

발견: 먼 쪽 서브는 공이 거의 카메라 쪽으로 날아와 화면에서 안 움직여서, 공 추적이 임팩트를 **75~230ms 늦게** 잡았다
(속도 6~29km/h 과대평가). 해결: **타구음**으로 임팩트를 다시 찾는다 (`analysis/serve_audio.py`).
- 소리 지연 = 타점~카메라 거리 / 343m/s (3D 카메라 모델로 계산, 먼 쪽 약 85ms)
- 녹화 자체의 음성-영상 어긋남(이 폰은 약 98ms)은 영상마다 가까운 쪽 서브(임팩트가 정확)로 자동 측정
- 3D 궤적이 네트 위치를 0.914~1.0m 아래로 지나면 **네트 폴트** 판정
- 가까운 쪽 서버는 토스가 항상 보이므로 토스 없는 '가까운 쪽 서브'는 랠리 샷으로 제외, '인' 서브 이후 같은 포인트에서는 서브를 찾지 않음

정답 12개 기준 결과 (`python tools/eval_gt.py models/tracknet.pt ...`):

| 방식 | 속도 평균 오차 | 판정(인/아웃/네트) | 놓침 |
|---|---|---|---|
| **TrackNet + 타구음 보정 (채택)** | **0.3 km/h** | **12/12** | 0 |
| TrackNet+WASB 앙상블 + 타구음 | 0.2 km/h | 10/12 | 2 |
| 맞춤 학습 TrackNet + 타구음 | 5.0 km/h | 9/12 | 2 |
| TrackNet, 타구음 보정 없음 | 8.4 km/h | 12/12 | 0 |

주의: 가까운 쪽 서브 3개의 정답 속도는 직접 확인한 임팩트·바운스가 TrackNet과 1프레임 이내로 같아 그 값을 썼다.
완전히 독립적으로 만든 먼 쪽 서브 5개만 보면 오차는 0~2km/h.

### 타구 라벨링 · AI 판독 정확도 (v0.5.1)

AI 샷 분석 패널의 `타구 라벨 (정답 입력)`을 열고, 영상을 보며 타구 순간에 키를 누른다.
`X` 서브 · `F` 포핸드 · `D` 백핸드 · `V` 발리 · `M` 스매시 · `L` 로브, Shift를 함께 누르면 먼 쪽 선수.
`,` / `.` 로 재생 속도를 0.25~2배로 바꿀 수 있다. 라벨은 프로젝트에 저장되고(`shot_labels`),
라벨을 단 포인트만 골라 AI 판독과 0.7초 이내로 맞춰 **종류별 찾은 비율·맞힌 비율·종류 혼동·놓친 타구**를 보여준다.

배경: 샘플 경기의 실제 Gemini 결과는 10포인트에서 포핸드 7 · 백핸드 0 · 발리 2만 기록했고,
서브 시각이 실제 임팩트보다 약 1초 이른 경우가 있었다. 랠리 판독이 얼마나 맞는지는
경기를 아는 사람이 단 라벨로만 공정하게 잴 수 있어 이 기능을 넣었다.

### 서브 구질 — 궤적 휘어짐 (v0.5.4)
- 서브 실측 때 임팩트 지점(3D)과 바운스 지점을 고정하고, 그 사이 공의 화면 경로를 중력+공기저항+일정한 추가 가속(옆·위)으로 맞춘다
  (`analysis/serve_spin.py`). 두 끝을 고정해서 카메라 하나로도 깊이가 흔들리지 않는다.
- 판정(오른손잡이 가정): 서버 왼쪽으로 2.5 m/s² 이상 휘면 슬라이스, 아래로 3 m/s² 이상 더 떨어지거나 오른쪽으로 휘며 떨어지면 킥,
  둘 다 작으면 플랫. 맞춤 오차가 1.5px(640×360 기준)를 넘거나 바운스를 0.3m 넘게 빗나가면 ‘미확인’.
- 검증(사용자 기록, 슬라이스 5개): 먼 쪽 3개는 −4.2~−5.0 m/s²로 슬라이스 판정(오차 4~5px → 0.6~1.1px), 2개는 미확인, 틀린 판정 0.
  정답에 플랫·킥이 아직 없어 구분 능력은 미검증. 가까운 쪽 서브는 공이 카메라에서 곧장 멀어져 대부분 미확인.
- 측정된 구질은 AI 샷 분석 결과의 서브 구질보다 우선한다(`serve_type_source: "measured"`, AI 값은 `serve_type_ai`).
- 첫 서브가 ‘라인 근접’이어도 세컨드 서브를 찾고, 같은 쪽에서 세컨드 서브가 나오면 첫 서브를 폴트(out)로 바꾼다.

### 랠리 타구 검출 · 타구별 판정 (v0.5.5)
- 서브 실측이 포인트마다 공을 끝까지 추적해 라켓 타구 시점과 친 쪽(가까운/먼)을 찾는다(`analysis/hit_detect.py`,
  결과 `cache/<파일>_hits.json`). 공이 **네트 테이프 높이 줄**을 내려가면(먼 쪽이 침) / 올라가면(가까운 쪽이 침) 한 번의 타구로 보고,
  정확한 순간은 그 사이 가장 그럴듯한 타구음으로 정한다.
  - 화면의 위아래 움직임만 보면 안 된다: 먼 코트에서는 공이 떨어지고 튀는 움직임이 대부분이다.
  - 카메라가 낮아 먼 서비스 박스 전체가 화면에서 네트 테이프보다 아래에 있다. 그래서 테이프 아래로 0.7초 안 갔다 돌아오고
    네트 밑줄을 넘지 않은 공은 바운스로 본다. 먼 쪽 타구는 공이 가까운 코트에 나타나거나 뚜렷한 타구음(≥3.5)이 있어야 인정한다.
  - 가까운 쪽 서버의 토스는 테이프 줄보다 높이 올라가므로 실측 서브 1.5초 전의 교차는 버린다. 폴트(넷·아웃) 뒤에는 다음 서브까지 아무것도 세지 않는다.
- 검증(1~6포인트 정답 21개, 1:08 기록은 프레임 확인으로 1:09.3에 고침): **21/21 검출, 친 쪽 21/21**, 헛 검출 2개(포인트가 끝난 뒤 공을 쳐서 돌려준 실제 타구).
  정답 없는 7~10포인트는 프레임으로 확인해 규칙(바운스 제거, 폴트 무시, 굴러가는 공 제외)을 보탰다.
- AI 샷 분석의 ‘방식’에서 **타구별**을 고르면 찾은 타구마다 친 쪽 코트 절반을 1.3초 클립(원본 해상도)으로 잘라 한 요청에 최대 20개씩 묻는다
  (`analysis/hit_shots.py`). 서브는 서브 실측 결과를 그대로 쓴다. 무료 등급 하루 요청 한도(모델당 약 20회)를 아끼는 구조.
- 결과(1~6포인트): 서브 7/7, 발리 2~3/4. **포·백은 같은 클립에서도 실행마다 8/14, 6/14로 흔들려 아직 약하다.**
  포즈(YOLO)로 접촉 순간 공이 몸 어느 쪽인지 재는 방법도 시험했지만 가까운 쪽의 뚜렷한 경우(3/3)만 맞고 몸 가까이 맞은 공과 먼 쪽은 쓸 수 없었다.

### 포/백은 스윙 방향으로 (v0.5.6)
- `analysis/swing_side.py`: 타구 순간 앞뒤 0.75초 동안 친 쪽 코트의 사람을 YOLO pose로 따라가고, 공이 가장 가까이 온 사람을
  친 선수로 본다(공이 안 보이면 스윙이 가장 큰 사람). 양 손목이 몸통에서 옆으로 얼마나 떨어졌는지를 **선수 기준**으로 잰다
  (가까운 쪽은 등을 보여 선수 오른쪽 = 화면 오른쪽, 먼 쪽은 마주 봐서 화면 왼쪽).
- 접촉 앞뒤 0.25초 안에서 0.15~0.25초 동안 손이 가장 크게 옆으로 움직인 양이 앞스윙이다. 오른손잡이는 오른쪽→왼쪽이면 포핸드,
  왼쪽→오른쪽이면 백핸드(한 손·양손 공통), 왼손잡이는 반대. 몸 높이의 0.10배보다 작으면 판정하지 않고 AI 답을 둔다.
- 먼 쪽 선수는 4K에서도 약 100px라 pose가 놓치므로(신뢰도 0.2) 2560으로 키워 돌린다(0.8).
- 결과(1~6포인트 포·백 정답 10개): **10/10** (같은 순간 Gemini 3.5는 4~6/10, 확대 클립·손잡이 힌트를 줘도 4/10).
  7~10포인트는 프레임으로 확인한 확실한 3개가 모두 맞았다. 타구당 약 3.5초(GPU).
- 경기 설정의 **왼손잡이 선수**(쉼표로 구분)를 보고 그 선수가 있는 쪽은 뒤집는다. 같은 쪽 두 선수의 손이 다르면 스윙으로 정하지 않는다.
  같은 정보는 Gemini 지시문에도 들어간다("이 코트 선수는 모두 오른손잡이입니다").
- 타구별 판정에서 AI가 forehand/backhand라고 한 타구만 스윙 결과로 바꾼다(발리·스매시·서브는 그대로, `racket_side`에는 기록).
  결과는 `cache/shots/<파일>_swings.json`에 타구별로 저장한다.
- **발리 / 그라운드스트로크**는 공 궤적으로 정한다(`hit_detect.mark_bounces`): 직전 타구 뒤 접촉 0.15초 전까지 공의 화면 y가
  봉우리(내려왔다 다시 올라감, 3px 이상)를 만들면 바운스, 아니면 발리. 서브 바로 다음 타구는 항상 바운스. 1~6포인트 14/14.
- 랠리 중간 타구를 AI가 serve라고 하면(서버 쪽 첫 타구가 아니면) smash로 고친다.
- 다른 코트 공: `hit_detect.own_court`(빠르게 움직이고 60% 이상이 이 코트 사이드라인 띠 안)로 타구 검출, 바운스·친 선수 판정,
  대시보드·주석 영상의 공 궤적까지 모두 이 코트 공만 쓴다.
- 서브 직후(사이에 랠리 타구 없이) 서버 쪽에서 나온 첫 타구는 서브 실측이 놓친 세컨드 서브로 본다. AI가 타구 없음이라 해도 공·소리가 잡은 타구는 바운스·스윙으로 종류를 정한다.
  공이 접촉 0.4초 전부터 안 보였으면 바운스는 '모름'(발리로 단정하지 않음).
- 7~11포인트 정답 추가 후 전체(44개): **36/44, 서브 17/17, 친 쪽 36/36**.

### 로브 랠리 · 서브 구질 (v0.5.7)
- **3D 공 궤적으로 빠진 타구 채우기** (`analysis/rally3d.py`): 공이 높이 떠서 화면상 네트 테이프 줄을 넘지 않는 로브·스매시 랠리는
  교차 방식이 못 본다. 추적한 공 경로를 중력+공기저항 3D 비행 조각(재투영 오차 1px 이하)으로 나누고, 코트 길이 방향 속도가
  뒤집히는 두 조각 사이를 타구로 본다. 친 쪽 = 친 뒤 공이 날아가는 방향의 반대편, 시각 = 두 조각을 마주 보게 이어 만나는 시점에 가장 가까운 타구음.
  교차 타구가 없는 곳에만 더하고(만난 곳이 그 쪽 코트, 높이 -1~4.5m일 때), 같은 쪽 교차 타구가 3D 구간 밖에 찍혔으면 시각을 고친다.
  4:01~4:12 로브 랠리 8타 모두 검출(이전 4타 놓침, 1타 0.9초 늦음). 정답 27개 전부 검출·친 쪽 27/27. 포인트당 약 5~20초.
- **서브 구질**: 타점(토스·소리로 추정)을 1.5×1.0×0.6m 안에서 움직이게 풀어 맞추니 가까운 쪽 서브 맞춤 오차가 3~6px → 1px 이하.
  먼 쪽 슬라이스 5/5. 가까운 쪽 슬라이스는 휘는 양이 -0.7~-1.9 m/s²로 작게 나와 1개만 슬라이스로 판정.
  이 영상의 플랫 서브 2개는 모두 네트 폴트라 쓸 궤적이 없어 **플랫은 아직 판정하지 않는다**(모름).
- 높은 발리와 스매시는 채점에서 같은 것으로 본다(사람이 봐도 애매함).
- **서브 동작으로 구질** (`analysis/serve_motion.py`, 사용자 제안): 친 뒤 0.45초 동안 서버의 두 발목 높이 차(키 대비) 최대값.
  가까운 쪽 서버는 플랫 0.21·0.24, 슬라이스 0.08~0.12로 갈렸다(뒷다리가 차오를 만큼 몸을 던짐). 사람마다 습관이라
  (먼 쪽 서버 슬라이스 0.13~0.36) 기준은 **같은 서버의 라벨된 서브에서 배우고**, 그 서브 자신의 라벨은 빼고 판정한다(정직한 채점).
  두 구질 예시가 겹치면(간격 0.04 미만) 쓰지 않는다. 공 휘어짐으로 확실한 슬라이스가 나오면 그것이 우선.
 놓친 것: 4:03~4:07 로브 랠리(공이 화면에서 줄곧 네트 테이프 줄보다 높아 교차가 없음).

### 랠리 샷 속도 (실험, 앱 미적용)

`analysis/rally_shots.py`: 궤적의 꺾임 중 선수 근처에서 진행 방향이 뒤집히는 것을 타구, 위로 꺾이는 것을 바운스로 보고
'타구→상대 코트 바운스' 구간의 속도를 계산한다. 샘플 경기에서는 공이 라켓 근처에서 흐려져 타구 순간에 궤적이 끊기는 경우가 많아
오검출·누락이 커서 앱에는 넣지 않았다. 선수 근처 공 검출이 좋아져야 한다 (타구 라벨이 그 학습 데이터가 될 수 있다).

### WASB 공 검출기 비교 (2026-10-09, 채택 안 함)

WASB-SBDT(NTT, BMVC 2023, MIT)의 테니스 사전학습 가중치를 붙여 비교했다 (`analysis/wasb.py`, `models/wasb_tennis.pth.tar`).

| | TrackNet | WASB | TrackNet+WASB 최대값 앙상블 |
|---|---|---|---|
| 서브 측정 | **10/10** | 3/10 | 9/10 |
| 궤적 커버리지 | 0.869 | 0.574 | 0.954 |

두 모델 모두 방송 화면 테니스 데이터로 학습됐지만 이 야간 동호인 영상에서는 TrackNet이 더 잘 맞는다.
앙상블은 공을 더 많이 잡지만 오검출도 늘어 서브 측정이 나빠졌다. 비교 명령:
`python tools/eval_serves.py models/tracknet.pt models/wasb_tennis.pth.tar "models/tracknet.pt+models/wasb_tennis.pth.tar"`

### 한계

- AI 샷 분석의 속도는 **AI 추정치**다 (±20km/h 수준). 서브는 `서브 속도 실측`으로 실측값으로 바꿀 수 있다.
- 횟수는 AI 판독이라 카메라 각도·화질에 따라 누락/오탐이 생길 수 있다. 검증 경고가 뜨면 신뢰도가 깎인다.
- 원본 4K HEVC에서 추출하면 약 실시간 속도(1분 영상 ≈ 1분)가 걸린다. 분석 구간이 15분을 넘으면 `자동`은 프록시를 쓴다.
